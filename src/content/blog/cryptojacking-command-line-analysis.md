> 이 글은 실제 분석 경험을 **교육용으로 재구성**한 것입니다. 기관·호스트·일시 같은 사고 맥락은
> 빼고, 지갑 주소와 채굴 풀 도메인은 마스킹했습니다.

## 출발점: 이상한 프로세스 하나

CPU 사용률이 계속 100%에 붙어 있는 호스트에서 다음과 비슷한 형태의 프로세스가 발견됐다고 합시다.

```text
./top -s python ./python3 --algo progpow-zano --pool ssl://<채굴풀>:<포트> \
      --user <지갑주소>.<워커명> --cpu-threads 0 --no-color --background
```

검체를 실행해 보고 싶은 유혹이 생기지만, 이 경우에는 **명령줄만으로 충분합니다**. 각 인자가 무엇을
뜻하는지만 읽으면 됩니다.

## 인자를 하나씩 읽기

| 조각 | 의미 | 판단 |
| --- | --- | --- |
| `./top`, `-s python` | 시스템 도구 이름을 빌린 런처가 프로세스 이름을 `python`으로 바꿈 | **위장** — 프로세스 목록에서 흔한 이름 뒤에 숨기 |
| `./python3` | 실제 실행되는 바이너리. 정상 인터프리터가 아니라 현재 디렉터리의 동명 파일 | **위장** — 정상 경로가 아닌 곳의 정상 이름 |
| `--algo progpow-zano` | 프라이버시 코인 채굴 알고리즘 | **목적 확정** — 이 인자를 쓰는 정상 업무는 없음 |
| `ssl://…` 채굴 풀 | TLS로 감싼 풀 연결 | **탐지 회피** — 평문 Stratum 시그니처를 피함 |
| `--cpu-threads 0` | 0 = 가용 코어 전부 | **자원 탈취** 의도 |
| `--background`, 출력 억제 | 터미널 없이 상주 | **은닉** |

알고리즘 이름 하나로 "이건 채굴기"가 확정되고, 나머지 인자는 그것이 **동의 없이 숨어서** 돌고
있다는 사실을 확정합니다. 실행 분석은 이 결론을 바꾸지 못하고, 오히려 위험만 키웁니다.

## ATT&CK으로 옮기기

| 기법 | ID | 근거 |
| --- | --- | --- |
| Resource Hijacking | T1496 | 채굴 알고리즘, 전 코어 사용 |
| Masquerading: Match Legitimate Name or Location | T1036.005 | `top`, `python`, `python3` 이름 차용 |
| Hide Artifacts | T1564 | 백그라운드 실행, 출력 억제 |
| Proxy | T1090 | 검열 우회형 풀, TLS 래핑 |

매핑은 보고서를 꾸미려는 것이 아닙니다. 기법 ID가 붙으면 "같은 기법을 쓰는 다른 흔적은 어디에
남는가"를 체계적으로 물을 수 있습니다. T1036.005라면 다른 호스트에서도 **정상 이름 + 비정상 경로**
조합을 찾으면 됩니다.

## IOC는 "누가 어떻게 쓰는가"로 나눈다

IOC를 한 표에 늘어놓으면 받는 쪽이 쓰기 어렵습니다. 쓰임새별로 나눕니다.

- **네트워크 차단용** — 채굴 풀 도메인과 그 상위 도메인. 방화벽·DNS 차단 목록으로 갑니다.
- **호스트 탐지용** — 파일명과 경로 조합(`./python3`가 정상 경로 밖에 있음), 프로세스 이름–실행 파일
  불일치. EDR 규칙이나 정기 점검 스크립트로 갑니다.
- **위협 인텔리전스용** — 지갑 주소, 알고리즘. 다른 사고와의 연결 고리를 찾는 데 씁니다.
- **행위 기반** — 장시간 CPU 포화 + 외부 TLS 장기 세션. 이름이 바뀌어도 남는 신호입니다.

네트워크 탐지 규칙(예: 스노트)으로 옮길 때는 TLS 때문에 페이로드 문자열에 기대기 어렵습니다. 풀
도메인의 SNI, 알려진 채굴 포트, 장기 세션 같은 메타데이터 쪽이 현실적입니다.

## 대응 순서가 중요한 이유

1. **증거 보존** — 프로세스 목록, 명령줄, 네트워크 연결, 검체 해시를 먼저 남깁니다. 프로세스를
   죽이면 명령줄이 사라집니다.
2. **격리** — 네트워크에서 분리합니다. 채굴은 소음이 크지만, 침입 경로는 조용할 수 있습니다.
3. **지속성 제거** — cron, systemd 유닛, macOS라면 launchd 항목까지. 지속성을 남긴 채 프로세스만
   죽이면 재부팅 뒤에 다시 올라옵니다.
4. **검체 격리 보관** — 삭제가 아니라 격리. 해시와 함께 보관해 재분석에 대비합니다.
5. **유입 경로 확인** — 채굴기는 결과이지 원인이 아닙니다. 약한 자격증명, 노출된 서비스, 취약한
   웹 애플리케이션 중 무엇이 문을 열었는지가 진짜 질문입니다.
6. **확산 점검** — 같은 IOC와 같은 기법(정상 이름 + 비정상 경로)을 다른 호스트에서 찾습니다.

## 배운 것

크립토재킹은 "그냥 채굴기"로 취급되기 쉽지만, 채굴기를 심을 수 있었던 공격자는 **다른 것도 심을 수
있었습니다**. 그래서 분석의 결론은 "채굴기 제거"가 아니라 "유입 경로를 닫았는가"여야 합니다.
